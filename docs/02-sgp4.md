# 2. SGP4: from elements to positions

A TLE tells you about an orbit. To screen for close approaches we need **positions**: where every object is at 12:00:00, 12:01:00, and so on. **SGP4** is the model that turns one into the other. This chapter explains what SGP4 is, why we have no choice but to use it, and how the Go port in [`pkg/sgp4`](../pkg/sgp4/) is organised.

## The problem: orbits aren't ellipses

In a textbook two-body problem (a point-mass Earth and one satellite), an orbit is a fixed ellipse and you can predict the satellite's position forever with Kepler's equation. Real orbits drift away from that ellipse because of:

| Effect | What it does | Matters most for |
|---|---|---|
| **Earth's oblateness** (J2, J3, J4 terms) | The equatorial bulge makes the orbit plane swing around (RAAN drift) and the ellipse rotate within it (perigee drift) | Everything; it is the biggest effect in LEO |
| **Atmospheric drag** | Steals energy, so the orbit shrinks and the satellite speeds up | LEO below ~1000 km |
| **Moon and Sun gravity** | Slow periodic wobbles in all the elements | High orbits (GPS, GEO, Molniya) |
| **Resonance with Earth's rotation** | An orbit whose period is a simple fraction of a day keeps meeting the same lumps in Earth's gravity field, so the effects accumulate instead of averaging out | 12-hour and 24-hour orbits |

## What SGP4 is

SGP4 ("Simplified General Perturbations 4") is an *analytical* model of those effects. There is no step-by-step numerical integration. Each element is written as a formula in time since epoch: secular drift (steady change) plus periodic terms. Given the TLE and a time `t`, you evaluate the formulas once and get the position. That's why it's fast: about 0.2 µs per position in this implementation.

Strictly, the deep-space part is called **SDP4**, but modern code (and this repo) treats SGP4/SDP4 as one model that picks the right branch automatically.

### Why we must use SGP4, not something "better"

A TLE's numbers are **not** the satellite's true orbital elements. They are the *mean elements* that make SGP4 best match the tracking data. Feed them into a different propagator, even a far more accurate one, and you get a *worse* answer, because that model interprets the numbers differently. The model and the data come as a pair.

This is also why the constants are WGS-72 (an Earth model from 1972) rather than the newer WGS-84. SGP4 was fitted with WGS-72, so TLEs are only consistent with WGS-72.

### Output frame: TEME

SGP4 returns position (km) and velocity (km/s) in the **TEME** frame (True Equator, Mean Equinox). This is an Earth-centred, non-rotating frame. Converting it to latitude/longitude needs Earth-rotation corrections, but **for collision screening we never need to**. Distance between two objects is the same in any frame, as long as both are in the same one, and SGP4 puts every object in TEME.

## The implementation

This is a port of **David Vallado's reference implementation** (2020 C++ release), from the paper *Revisiting Spacetrack Report #3* (AIAA 2006-6753). Vallado's version is the de facto standard. It fixed dozens of bugs in the 1980 original, and every serious implementation is tested against his output, including python-sgp4, Orekit, and CelesTrak's own tools.

Porting rather than re-deriving was deliberate. The goal is "the same answers as everyone else", and the shortest path there is to follow the reference line by line. Variable names (`cc1`, `xmdf`, `nodem`, …) are kept from Vallado's code so anyone can compare the two side by side.

### The API

```go
el, _ := tle.Parse(name, line1, line2)
sat, err := sgp4.New(el)              // precompute everything that doesn't depend on time
r, v, err := sat.Propagate(90.0)      // 90 minutes after the TLE epoch
r, v, err = sat.PropagateTo(someTime) // or at an absolute time.Time
```

`r` and `v` are `[3]float64` arrays (TEME, km and km/s), returned by value, so the hot path allocates nothing.

### Step 1: initialisation (`New`)

`New` converts the TLE to SGP4's internal units (radians, radians per minute) and precomputes every quantity that doesn't depend on time. That's a few dozen coefficients, and about twice as many for deep-space orbits. Doing this once per satellite is what makes each later `Propagate` call cheap. Highlights:

- **Un-Kozai the mean motion.** TLEs publish mean motion in the "Kozai" convention, and SGP4's formulas use "Brouwer" mean motion. The first few lines of `init` convert one to the other.
- **Pick the drag model.** If perigee is below 220 km, a simplified drag model is used (`isimp`). Below 156 km, the atmospheric density parameters are adjusted.
- **Pick near-Earth or deep space.** Orbits with a period of 225 minutes or more get the deep-space treatment. `dscom` computes the lunar and solar terms and `dsinit` sets up the secular rates. For resonant orbits, `dsinit` also sets up the resonance integrator: `irez = 1` for 24-hour orbits, `irez = 2` for eccentric 12-hour orbits.
- **Sanity check.** Like Vallado's `sgp4init`, `New` propagates to `t = 0` and returns any error. An element set that can't be evaluated at its own epoch isn't usable.

### Step 2: propagation (`Propagate`)

For a time `t` minutes from epoch, `Propagate` runs these steps in order:

1. **Secular effects.** Apply the steady drift from gravity (J2 makes RAAN and perigee rotate) and drag (the orbit shrinks, so mean motion increases).
2. **Deep-space effects** (`dspace`), for long-period orbits. Apply secular lunar/solar drift and integrate the resonance terms.
3. **Lunar-solar periodics** (`dpper`), for long-period orbits. Add the periodic wobbles. At low inclination this uses *Lyddane's modification* to avoid dividing by sin(inclination) ≈ 0.
4. **Long-period periodics** from the J3 term.
5. **Solve Kepler's equation** by Newton iteration, to find where on the ellipse the object is.
6. **Short-period periodics.** Small corrections that oscillate twice per orbit.
7. **Build position and velocity vectors** from the final elements.

### Error handling

Some TLEs describe objects that are about to re-enter, or orbits that drag has pushed into nonsense. `Propagate` returns a `*sgp4.Error` with Vallado's error codes:

| Code | Meaning | Typical cause |
|---|---|---|
| 1 | Mean eccentricity out of range | Drag model breaking down for a decaying object |
| 2 | Mean motion ≤ 0 | Garbage elements |
| 3 | Perturbed eccentricity out of range | Lunar-solar terms pushing a near-zero-eccentricity orbit below zero |
| 4 | Semi-latus rectum < 0 | Orbit has become hyperbolic or degenerate |
| 6 | Radius < 1 Earth radius | **The object has decayed**, i.e. it is underground |

These errors are normal with real data. In the screener, an object that fails is dropped from the time steps where it fails. It is not a reason to abort the run.

### The one deliberate change: no hidden state

Vallado's `sgp4()` **writes to the satellite record** on every call. The deep-space resonance integrator caches its last position, so the next call can continue from there instead of starting at epoch. It also stores the latest error code and a few recomputed coefficients.

That's a problem for milestone 3, where many goroutines will propagate the same satellites at the same time. Shared mutable state would mean data races, and results that depend on which goroutine asked first.

This port makes `Propagate` **pure**. It reads the `Satellite` and never writes to it:

- Coefficients that Vallado overwrites for deep-space orbits (`aycof`, `xlcof`, `con41`, `x1mth2`, `x7thm1`) are held in local variables.
- The resonance integrator **always restarts from epoch**. That gives bit-for-bit the same answer, because the integrator takes fixed 720-minute steps starting at epoch either way. Resuming from a cache just skips steps that would have been computed identically. The cost is a few extra steps per call for resonant objects: 14 steps for a 7-day screen, which is negligible.

`TestPropagateIsPure` checks this by propagating every verification satellite forwards and then backwards in time, and requiring identical results. The test suite also passes under `go test -race`.
